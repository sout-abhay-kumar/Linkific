
# Backend Interview Questions – SmartSpend (ExpenseTracker)

This document contains three backend interview questions based on the implementation of my SmartSpend ExpenseTracker project.

## 1. What is FastAPI, and why did you choose it for your project?

### Answer

FastAPI is a modern Python web framework used to build APIs. It supports automatic API documentation, request validation, type hints, and asynchronous programming.

I chose FastAPI for my ExpenseTracker project because:

- **Performance:** It is designed for building high-performance APIs.
- **Automatic Documentation:** It generates interactive API documentation using Swagger UI.
- **Data Validation:** It integrates with Pydantic to validate incoming request data.
- **Python Support:** It allows me to use Python for backend development.
- **SQLAlchemy Integration:** It can work with SQLAlchemy to communicate with PostgreSQL.

### How I Used It in My Project

I used FastAPI to build REST API endpoints for:

- Google authentication.
- Creating, retrieving, updating, and deleting transactions.
- Retrieving categories.
- Managing monthly budgets.
- Fetching dashboard information.

### Example

```python
@app.get("/api/transactions")
def get_transactions():
    return {"message": "Transactions retrieved successfully"}
```

This is a simplified example of a FastAPI GET endpoint.

## 2. How does your backend communicate with PostgreSQL?

### Answer

My backend communicates with PostgreSQL using SQLAlchemy, which is an Object Relational Mapper (ORM).

An ORM allows developers to interact with database tables using Python classes and objects instead of writing SQL queries for every operation.

### Database Communication Flow

1. The frontend sends an HTTP request to the FastAPI backend.
2. FastAPI receives the request.
3. The backend validates the incoming data.
4. SQLAlchemy executes the required database operation.
5. PostgreSQL processes the query.
6. The database returns the requested data or operation result.
7. FastAPI sends a JSON response to the frontend.

### Database Tables in My Project

| Table | Purpose |
|---|---|
| `users` | Stores user information |
| `transactions` | Stores income and expense records |
| `categories` | Stores transaction categories |
| `budgets` | Stores monthly budget information |

### Example

A simplified SQLAlchemy query to retrieve transactions:

```python
transactions = (
    db.query(Transaction)
    .filter(Transaction.user_id == current_user.id)
    .all()
)
```

**Explanation:**

- `db.query(Transaction)` starts a query for transaction records.
- `filter()` selects records belonging to the authenticated user.
- `all()` retrieves the matching records.

Filtering by the authenticated user's ID helps ensure that users access only their own transactions.

## 3. How does authentication work in your ExpenseTracker application?

### Answer

My ExpenseTracker application uses Google Sign-In for user authentication and JSON Web Tokens (JWT) for authenticated communication between the frontend and backend.

Google Sign-In verifies the user's identity, while JWT is used to authenticate subsequent requests to protected backend endpoints.

### Authentication Flow

1. The user clicks the Google Sign-In button on the React frontend.
2. Google Identity Services provides a Google ID token.
3. The frontend sends this ID token to the FastAPI backend.
4. The backend verifies the token with Google's authentication mechanism.
5. The backend identifies the user and creates a user record if one does not already exist.
6. The backend generates an application JWT.
7. The frontend uses the application JWT when accessing protected API endpoints.
8. The backend verifies the JWT before allowing access to protected resources.

### Authentication Diagram

```text
React Frontend
      |
      | Google Sign-In
      v
Google Identity Services
      |
      | Google ID Token
      v
FastAPI Backend
      |
      | Verify Google ID Token
      v
Find or Create User
      |
      | Generate Application JWT
      v
React Frontend
      |
      | JWT in API Request
      v
Protected FastAPI Endpoint
      |
      | Verify JWT and Authorize User
      v
PostgreSQL
```

### Important Difference

| Google ID Token | Application JWT |
|---|---|
| Issued by Google | Generated by my backend |
| Establishes the user's Google identity | Authenticates requests to my application |
| Verified by the backend | Verified by the backend |
| Used during Google Sign-In | Used for subsequent protected API requests |

### Why Is JWT Useful?

- It allows the backend to authenticate API requests.
- It avoids requiring the user to sign in with Google for every request.
- It can carry information such as the user ID and token expiration.
- It supports stateless authentication when implemented appropriately.
